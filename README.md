# Коннектор amoCRM → Claude

MCP-сервер, через который Claude читает сделки, события, звонки и задачи из amoCRM и считает показатели воронки.

Claude может читать и изменять данные: этапы, ответственных, поля, теги, задачи, примечания, создавать сделки. Удаления нет. Любое изменение сначала показывается как «было → станет» и применяется только после вашего подтверждения. Сервер не передаёт в Claude имена, телефоны, email и адреса клиентов. Тексты переписки тоже не передаются. Токен amoCRM хранится только на сервере.

## Что умеет

| Инструмент | Что делает |
| --- | --- |
| `get_reference` | воронки, этапы с id, менеджеры, поля, причины отказа, источники |
| `search_leads` | сделки за период с фильтрами по воронке, этапу, менеджеру, каналу |
| `get_lead` | одна сделка: хронология, задачи, звонки |
| `get_events` | поток событий по сделкам за период |
| `get_tasks` | открытые и просроченные задачи |
| `get_unsorted` | заявки, которые висят в «Неразобранном», и сколько они ждут |
| `get_funnel_metrics` | время до первой попытки и до первого контакта, доля заявок без ответа, конверсия в замер и договор, причины отказов — по каналам, менеджерам или месяцам |
| `find_stalled_leads` | открытые сделки без задачи или без изменений N дней |
| `diagnose_lead_feed` | диагностика: какие звонки, сообщения и события есть у сделки и её контактов |
| `phone_hash` | хеши телефонов сделки для поиска повторных клиентов, без самих номеров |
| `update_leads` | **изменение** до 50 сделок: этап, воронка, ответственный, бюджет, причина отказа, теги, доп. поля |
| `create_tasks` | **создание** задач по сделкам, например на дожим |
| `complete_task` | **закрытие** задачи с результатом |
| `add_notes` | **примечания** в сделки |
| `create_lead` | **создание** сделки, например для заказов мимо отдела продаж |
| `get_audit_log` | журнал всех изменений, сделанных через коннектор |

## Шаг 1. Токен amoCRM (делает администратор)

1. amoCRM → «Настройки» → «Интеграции» → «Создать интеграцию» → частная интеграция.
2. Название: «Claude». Доступ: данные аккаунта. Токен действует с правами пользователя, который создал интеграцию: для изменения данных у него должны быть права на редактирование сделок и задач.
3. Во вкладке «Ключи и доступы» сгенерировать **долгосрочный токен**, срок 1 год.
4. Передать токен тому, кто разворачивает сервер. Лично, не в общих чатах и не в переписке с ИИ.

Если в аккаунте нет долгосрочных токенов, используйте OAuth 2.0 по документации amoCRM. Обычный access token живёт сутки, и его придётся обновлять.

## Шаг 2. Сервер

Нужен VPS с Docker, доменом и HTTPS. Сервер должен быть доступен из интернета: Claude подключается к нему из облака Anthropic, а не с вашего компьютера. Подойдёт любой VPS за 300–600 ₽ в месяц.

```bash
git clone https://github.com/Strax777666/mcpamo.git amocrm-mcp && cd amocrm-mcp
cp .env.example .env
nano .env        # заполнить AMO_SUBDOMAIN, AMO_TOKEN, MCP_SECRET
docker build -t amocrm-mcp .
docker run -d --name amocrm-mcp --restart unless-stopped --env-file .env \
  -v amocrm-audit:/data -p 127.0.0.1:8000:8000 amocrm-mcp
```

HTTPS проще всего получить через Caddy. Пример файла `/etc/caddy/Caddyfile`:

```
mcp.ваш-домен.ru {
    reverse_proxy 127.0.0.1:8000
}
```

Адрес коннектора получится таким:

```
https://mcp.ваш-домен.ru/mcp/<MCP_SECRET>
```

## Шаг 3. Подключение в Claude

1. Claude → «Настройки» → «Коннекторы» → «Добавить свой коннектор».
2. Вставить адрес из шага 2.
3. В чате нажать «+» → «Коннекторы» и включить коннектор.

## Шаг 4. Первая настройка

1. Попросите Claude: «вызови get_reference».
2. По ответу впишите в `.env`:
   - `MEASURE_STATUS_IDS` — id этапов, означающих замер;
   - `CONTRACT_STATUS_IDS` — id этапов договора;
   - `CHANNEL_FIELD_ID` — id поля с каналом заявки, если канал хранится в поле, а не в тегах.
3. Перезапустите контейнер: `docker restart amocrm-mcp`.

## Безопасность

- **Изменения только с подтверждением.** Claude сначала вызывает инструмент в режиме предпросмотра и показывает, что изменится. Кроме того, Claude спрашивает разрешение на каждый вызов инструмента коннектора — не включайте для него «разрешать всегда», пока не привыкнете к работе.
- **Не больше 50 объектов за раз, удаления нет.** Сделку можно закрыть с причиной отказа, но не удалить.
- **Журнал.** Все изменения пишутся в `/data/audit.log`, их можно посмотреть через `get_audit_log`. В самой amoCRM изменения тоже видны в истории сделки.
- **Выключить запись.** `WRITE_ENABLED=0` в `.env` и `docker restart amocrm-mcp` — коннектор останется только для чтения.

- **Адрес коннектора = пароль.** Любой, у кого есть адрес с `MCP_SECRET`, может читать и менять данные. Не публикуйте его. Если адрес утёк, смените `MCP_SECRET`, перезапустите контейнер и обновите адрес в Claude.
- **Отключение за минуту.** Отзовите токен в настройках интеграции amoCRM. Коннектор сразу перестанет получать данные.
- **Файл `.env`** лежит только на сервере, в репозиторий не коммитится.
- **Юридическая проверка.** Место хостинга и передачу данных внешнему сервису согласуйте с юристом с учётом 152-ФЗ.

## Ограничения первой версии

- Код проверен на тестовых данных, но не на вашем аккаунте. При первом запуске сверьте цифры с фильтрами в amoCRM (критерии приёмки — в ТЗ).
- Звонки попадают в расчёт, только если телефония записывает их в amoCRM как примечания со звонком.
- Сообщения из мессенджеров попадают в расчёт, только если мессенджеры подключены к amoCRM.
- Если канал не хранится ни в поле, ни в первом теге сделки, логику функции `_channel` в `server.py` нужно доработать под вашу CRM.

## Изменения в версии 1.1

- Звонки (Sipuni) и сообщения (Wazzup) теперь берутся не только из сделки, но и из привязанных контактов. amoCRM показывает их в ленте сделки, но хранит у контакта.
- Причина отказа читается из доп. поля `LOSS_REASON_FIELD_ID` (по умолчанию 541817), а не только из системного поля amoCRM.
- Новый инструмент `diagnose_lead_feed` показывает, где физически лежат звонки и переписка по конкретной сделке.

Обновление: заменить `server.py`, добавить в `.env` строку `LOSS_REASON_FIELD_ID=541817`, затем выполнить
`docker build -t amocrm-mcp . && docker rm -f amocrm-mcp && docker run -d --name amocrm-mcp --restart unless-stopped --env-file .env -v amocrm-audit:/data -p 127.0.0.1:8000:8000 amocrm-mcp`.

## Изменения в версии 1.2

- Массовый расчёт (`get_funnel_metrics`) запрашивает переписку у контактов по списку контактов, по 10 за раз, так же как карточка сделки. Запрос без списка amoCRM отдавал неполностью.
- За длинный период (полгода и больше) расчёт идёт дольше: по одному запросу на каждые 10 контактов. Если Claude не дожидается ответа, считайте по месяцам.

Обновление: заменить `server.py`, `.env` не менять, затем выполнить ту же команду, что для версии 1.1 (том `amocrm-audit` должен остаться подключённым к `/data`).

## Изменения в версии 1.3

- Исправлен массовый расчёт: переписка мессенджеров (Wazzup) приходит от amoCRM как события сделки, а версия 1.2 искала её по id контакта и отбрасывала. Теперь сообщения относятся к своей сделке. За 1–26 сентября 2026 доля заявок без ответа изменилась с 52,4% на 27,1%, медиана до первой попытки в рабочее время — с 213 до 12 минут.
- Одно и то же событие больше не считается дважды, если пришло и по сделке, и по контакту.
- При обрыве соединения со стороны amoCRM запрос повторяется, а не падает.

Обновление: как для версии 1.2, `.env` не менять.

## Изменения в версии 1.4

- Порог состоявшегося звонка — 45 секунд (`CALL_OK_SECONDS`): Sipuni включает гудки в длительность, и звонки до ~40 с часто оказываются недозвоном.
- `get_funnel_metrics`, `search_leads` и `find_stalled_leads` по умолчанию считают только основную воронку (`MAIN_PIPELINE_ID`, по умолчанию 3388186 «Воронка»). `pipeline_id=0` — все воронки.

Обновление: заменить `server.py`, в `.env` поставить `CALL_OK_SECONDS=45` (иначе останется старый порог), пересобрать контейнер той же командой.
